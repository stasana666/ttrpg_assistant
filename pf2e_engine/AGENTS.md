# PF2E Engine

Canonical project instructions. CLAUDE.md redirects here.

## Purpose
- Core headless PF2E game-mechanics engine: battle state, maps, players, resources, actions, mechanics, inventory, runtime DSL, transformations, continuations, and AST state comparison.
- Public headers live in `include/pf2e_engine/`; implementations live in `src/`; data lives in `data/`; tests live in `tests/`.
- Keep this code independent of assistant GUI/audio and analyzer strategy implementations.

## Key Concepts
- Target `pf2e_engine` links `nlohmann_json`, `nlohmann_json_schema_validator`, `ttrpg_parse`, and `expr`.
- `TBattle` orchestrates rounds, turns, initiative, resources, effects, scheduled tasks, transformations, action history, the encounter clock, relations and battle end state.
- The engine talks to outside systems only through `IInteractionSystem`; assistant, analyzer, and tests provide concrete implementations.
- `TGameObjectFactory` loads JSON definitions recursively from `pf2e_engine/data`, creates typed objects by registered ids, and builds the immutable `TAbilityRules` that every battle shares. Generated by-name types register with `RegisterType<T>(jsonType)`.
- Creature, inventory and condition types and most PF2e rules are generated from `.ttrpg` schemas in `data/schemas/`; `TCreature` is a generated `GameEntity` with no handwritten subclass.
- Abilities come from grants on current creature, race, class and weapon features. `TBattle::AvailableActions` and `Execute(option)` enumerate and run them; typed reactions run through reaction windows opened by compiled rules.
- Compiled `.ttrpg` action bodies are the preferred path. Legacy JSON pipelines, parsed by `TActionReader` with blocks registered in `src/actions/action_reader.cpp`, remain for unmigrated actions and evaluate runtime DSL from `src/dsl/`.
- Rollback and resume depend on `TTransformator`, `TSavepointStackUnwind`, continuation helpers and AST state comparison. Runtime invariants are documented in `include/pf2e_engine/common/AGENTS.md`.

## Build/Test
- Build engine: `cmake --build build --target pf2e_engine`.
- Broad check: `ctest --test-dir build --output-on-failure`; see `tests/AGENTS.md` for targets and shared fixtures.
- Headless encounter: `./build/analyzer/analyzer --scenario fighter-wolves --iterations 10`.

## Extending Actions
- Prefer compiled `.ttrpg` bodies for new rules. Extend the compiler through small generic runtime adapters and keep PF2e formulas in rule declarations.
- For legacy JSON pipelines, prefer exposing a DSL property or function in `src/dsl/builtins.cpp` before adding an action-block class.
- Add an action block only for C++ side effects such as RNG, transformations, scheduling, prompts, or named outputs beyond `let`. Update the header/source, `pf2e_engine/src/action_blocks/CMakeLists.txt`, includes, and `TPipelineReader::kFunctionMapping`.

## Pitfalls
- Do not edit generated headers/sources in `build/generated`; edit schemas or codegen instead.
- Data-loading tests depend on generated `cpp_config.h` and `kRootDirPath`; avoid hard-coded absolute paths.
- Mutations that bypass `TTransformator` can survive rollback and should be caught by AST tests.
- Do not mix direct legacy `TEffectManager::AddEffect(Frightened)` with the generated fear methods in new rules.
- Use local docs under `data/`, `data/schemas/`, `src/dsl/`, `include/pf2e_engine/common/`, and `tests/` before loading unrelated engine context.
